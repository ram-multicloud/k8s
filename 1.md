## 1. Google's History with Containers

### Notes

- Google has a history of running containers in their production environments.
- To manage these containers they built orchestration platforms:
  - Omega
  - Borg
- When Docker was adopted, Google created an open-source container orchestration platform called **Kubernetes** and donated it to the **CNCF**. `Cloud Native Computing Foundation`
- Kubernetes is written in **Golang**.
- Kubernetes in its early versions was focused only on Docker.

### Explanation

- **Container orchestration** means automatically deciding where containers run, restarting them when they fail, scaling them up or down, and connecting them together. Running one container is easy (`docker run`); running thousands across many machines needs a system to manage them.
- Google was running containers at massive scale long before Docker made them popular. **Borg** was their internal system for this, and **Omega** was a later internal experiment. Kubernetes is the open-source system built on the lessons learned from Borg.
- **CNCF** (Cloud Native Computing Foundation) is a vendor-neutral foundation that hosts Kubernetes. Donating it there means no single company controls it, which is a big reason for its wide adoption.
- **Golang** matters because most of the Kubernetes ecosystem (kubectl, operators, many tools) is also written in Go.
- In the early days Kubernetes could only work with Docker as its container engine. That was a limitation, which led to the interfaces described next.

## 2. The Three Interfaces: CRI, CNI, CSI

### Notes

- Kubernetes needs to speak with:
  - container engine
  - networks
  - storage
- To standardize this communication, Kubernetes has 3 interfaces:
  - **CRI** (Container Runtime Interface)
  - **CNI** (Container Network Interface)
  - **CSI** (Container Storage Interface)
- While installing Kubernetes there is **no default CNI**.

### Explanation

Kubernetes itself does not run containers, build networks, or manage disks. It delegates to plugins. To let anyone plug in their own tool, it defines a standard "contract" (interface) for each area. Think of it like a USB port: any device that follows the standard works.

| Interface | Talks to | Purpose | Common examples |
|-----------|----------|---------|-----------------|
| **CRI** – Container Runtime Interface | Container engine | Start, stop and manage containers | containerd, CRI-O |
| **CNI** – Container Network Interface | Network | Give pods IP addresses and let them communicate | Calico, Flannel, Cilium |
| **CSI** – Container Storage Interface | Storage | Create and attach volumes to pods | AWS EBS CSI driver, Azure Disk CSI driver |

**Why "no default CNI" matters (practical point):**

- When you install a cluster (for example with `kubeadm`), Kubernetes does **not** come with pod networking pre-configured.
- Until you install a CNI plugin, nodes typically show `NotReady` and pods (like CoreDNS) stay `Pending`.
- So after creating a cluster, installing a CNI is a required step.

**Docker note:** Because of CRI, Kubernetes is no longer tied to Docker. Docker support through the old built-in shim was removed in Kubernetes 1.24; runtimes like containerd are used directly now. Docker-built images still work fine, since they follow the standard image format.

## 3. Terms

- Cluster

### Explanation

A **cluster** is a group of machines working together as one system. In Kubernetes, you talk to the cluster as a whole, and it decides which machine runs what.

## 4. Kubernetes Cluster

### Notes

- A Kubernetes cluster is made up of **Nodes**.
- A Node can be a physical or virtual machine.
- There are two types of Nodes:
  - **Master Nodes**: they manage the cluster.
  - **Worker Nodes**: they run the workloads (application containers).

Diagrams from the original post:

- https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s1.png
- https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s2.png

### Explanation

- A **Node** is simply one machine (a physical server or a VM such as an AWS EC2 instance or Azure VM) that is part of the cluster.
- **Master nodes** are the "brain". They store the cluster's desired state, decide where new workloads should run, and watch for failures. In current Kubernetes terminology this is called the **control plane**, and the term "master" is being phased out.
- **Worker nodes** are the "muscle". They actually run your application containers (inside pods).

```
                +----------------------------+
                |   Master Node(s)           |
                |   (control plane)          |
                |   manages the cluster      |
                +-------------+--------------+
                              |
              +---------------+---------------+
              |                               |
      +-------v--------+              +-------v--------+
      |  Worker Node 1 |              |  Worker Node 2 |
      |  runs app      |              |  runs app      |
      |  containers    |              |  containers    |
      +----------------+              +----------------+
```

**Flow in simple words:** you tell the master what you want (for example "run 3 copies of this app"); the master decides which workers should run them; the workers start the containers.
