# Kubernetes IAM: Users, Groups and Namespace-Scoped Access

## 1. Concepts

Kubernetes has no `User` or `Group` objects. You cannot run `kubectl create user`. Identity comes from the **authentication** layer, and permissions come from **RBAC** (authorization).

| Layer | Question answered | How it works |
|---|---|---|
| Authentication (AuthN) | Who are you? | Client certificate, OIDC token, service account token, cloud IAM |
| Authorization (AuthZ) | What can you do? | RBAC: `Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding` |
| Admission | Is the request allowed by policy? | Admission controllers (PSA, quotas, etc.) |

With **client certificates** (used in this guide):

- Certificate `CN` (Common Name) becomes the **username**.
- Certificate `O` (Organization) becomes the **group**. Multiple `O=` values give multiple groups.

RBAC objects:

| Object | Scope | Purpose |
|---|---|---|
| `Role` | One namespace | Set of permissions (verbs on resources) |
| `RoleBinding` | One namespace | Grants a Role (or ClusterRole) to users/groups/service accounts in that namespace |
| `ClusterRole` | Cluster-wide | Permissions for cluster-scoped resources or reusable rules |
| `ClusterRoleBinding` | Cluster-wide | Grants a ClusterRole across all namespaces |

RBAC is **additive only**. There are no deny rules. No binding means no access.

## 2. Scenario

| Item | Value |
|---|---|
| Username | `ram` |
| Group | `dev-team` |
| Namespace | `dev` |
| Access | Manage pods, deployments, services, configmaps in `dev` only |
| Everything else | Denied |

## 3. Prerequisites

- A running cluster (minikube, kind, kubeadm, etc.)
- `kubectl` configured with **cluster-admin** access
- `openssl` installed

Verify:

```bash
kubectl cluster-info
kubectl auth can-i '*' '*' --all-namespaces
```

The second command must print `yes`.

## 4. Step-by-Step

### Step 1: Create the namespace

```bash
kubectl create namespace dev
kubectl get ns dev
```

### Step 2: Generate a private key and CSR for the user

The `/CN=` is the username and `/O=` is the group.

```bash
mkdir -p ~/k8s-users/ram && cd ~/k8s-users/ram

openssl genrsa -out ram.key 2048
openssl req -new -key ram.key -out ram.csr -subj "/CN=ram/O=dev-team"
```

Check the subject:

```bash
openssl req -in ram.csr -noout -subject
```

### Step 3: Submit a CertificateSigningRequest to Kubernetes

The cluster CA signs the certificate. `expirationSeconds: 86400` makes it valid for 1 day (use a longer value for real users).

```bash
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ram
spec:
  request: $(base64 -w0 < ram.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages:
  - client auth
EOF
```

> On macOS use `base64 < ram.csr | tr -d '\n'` instead of `base64 -w0`.

### Step 4: Approve the CSR and fetch the signed certificate

```bash
kubectl get csr
kubectl certificate approve ram
kubectl get csr ram -o jsonpath='{.status.certificate}' | base64 -d > ram.crt
```

Inspect the certificate:

```bash
openssl x509 -in ram.crt -noout -subject -dates
```

Expected subject contains `CN = ram, O = dev-team`.

### Step 5: Build a kubeconfig for the user

```bash
# Cluster details from the admin kubeconfig
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
CLUSTER=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}')
kubectl config view --raw --minify \
  -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.crt

# Cluster
kubectl config set-cluster $CLUSTER \
  --server=$SERVER \
  --certificate-authority=ca.crt \
  --embed-certs=true \
  --kubeconfig=ram.kubeconfig

# User credentials
kubectl config set-credentials ram \
  --client-certificate=ram.crt \
  --client-key=ram.key \
  --embed-certs=true \
  --kubeconfig=ram.kubeconfig

# Context (default namespace = dev)
kubectl config set-context ram-ctx \
  --cluster=$CLUSTER \
  --user=ram \
  --namespace=dev \
  --kubeconfig=ram.kubeconfig

kubectl config use-context ram-ctx --kubeconfig=ram.kubeconfig
```

If the cluster CA is not in your admin kubeconfig as data (for example it uses a file path), copy that CA file instead.

### Step 6: Confirm the user is authenticated but has no permissions yet

```bash
kubectl --kubeconfig=ram.kubeconfig get pods
```

Expected:

```
Error from server (Forbidden): pods is forbidden: User "ram" cannot list resource "pods" in API group "" in the namespace "dev"
```

This proves authentication works (the server knows the user is `ram`) and authorization denies everything by default.

### Step 7: Create a Role in the `dev` namespace

```bash
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-editor
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log", "services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
EOF
```

### Step 8: Bind the Role to the **group** (not the user)

Binding to the group means any future user with `O=dev-team` in their certificate gets the same access automatically.

```bash
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-editor-binding
  namespace: dev
subjects:
- kind: Group
  name: dev-team
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: dev-editor
  apiGroup: rbac.authorization.k8s.io
EOF
```

To bind to a single user instead, use:

```yaml
subjects:
- kind: User
  name: ram
  apiGroup: rbac.authorization.k8s.io
```

Verify the objects:

```bash
kubectl get role,rolebinding -n dev
kubectl describe rolebinding dev-team-editor-binding -n dev
```

## 5. Test and Validate

### 5.1 Quick check as admin using impersonation

No kubeconfig switch needed:

```bash
kubectl auth can-i create deployments -n dev --as=ram --as-group=dev-team
kubectl auth can-i list pods        -n dev --as=ram --as-group=dev-team
```

Expected: `yes` for both.

List everything the user can do in the namespace:

```bash
kubectl auth can-i --list -n dev --as=ram --as-group=dev-team
```

### 5.2 Positive tests as the real user

```bash
export KUBECONFIG=~/k8s-users/ram/ram.kubeconfig

kubectl auth whoami            # shows username and groups (K8s 1.28+)
kubectl run nginx --image=nginx
kubectl get pods
kubectl create deployment web --image=nginx --replicas=2
kubectl get deployments
kubectl expose deployment web --port=80
kubectl logs deploy/web
kubectl delete deployment web
```

All should succeed in the `dev` namespace.

### 5.3 Negative tests (must be denied)

```bash
# Other namespaces
kubectl get pods -n default
kubectl get pods -n kube-system
kubectl get pods --all-namespaces

# Resources not in the Role
kubectl get secrets -n dev
kubectl get nodes
kubectl get namespaces

# Cluster-level actions
kubectl create namespace hacked
kubectl create clusterrole x --verb=get --resource=pods
```

Each must return `Forbidden`.

Equivalent checks as admin:

```bash
kubectl auth can-i get pods     -n default --as=ram --as-group=dev-team   # no
kubectl auth can-i get secrets  -n dev     --as=ram --as-group=dev-team   # no
kubectl auth can-i get nodes               --as=ram --as-group=dev-team   # no
```

### 5.4 Validation checklist

| Test | Expected |
|---|---|
| `auth whoami` shows `ram` and `dev-team` | Pass |
| Create/list/delete pods and deployments in `dev` | Allowed |
| Any operation in `default` / `kube-system` | Forbidden |
| Read secrets in `dev` | Forbidden |
| Cluster-scoped resources (nodes, namespaces) | Forbidden |
| `auth can-i --list -n dev` matches the Role rules | Pass |

## 6. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `Unauthorized` (401) | Certificate not signed by cluster CA, expired, or wrong key | Check `openssl x509 -noout -dates`, regenerate CSR |
| `Forbidden` (403) in `dev` | Missing or wrong RoleBinding, group name mismatch | `kubectl describe rolebinding -n dev`; check `O=` matches `subjects.name` exactly (case-sensitive) |
| `no such host` / connection refused | Wrong `--server` in kubeconfig | Re-check `SERVER` value |
| CSR stuck in `Pending` | Not approved | `kubectl certificate approve <name>` |
| Group permissions not applied | Certificate issued without `O=` | Recreate the CSR with `-subj "/CN=ram/O=dev-team"` |

Useful debug commands:

```bash
kubectl get csr
kubectl auth can-i --list -n dev --as=ram --as-group=dev-team
kubectl get rolebinding,clusterrolebinding -A -o wide | grep -E 'ram|dev-team'
```

## 7. Cleanup

```bash
unset KUBECONFIG
kubectl delete rolebinding dev-team-editor-binding -n dev
kubectl delete role dev-editor -n dev
kubectl delete csr ram
kubectl delete namespace dev
rm -rf ~/k8s-users/ram
```

> Kubernetes cannot revoke a client certificate. Removing the RoleBinding removes access. Short certificate lifetimes limit the exposure window.

## 8. Using Built-in ClusterRoles Instead of a Custom Role

Instead of writing a Role, you can reuse a built-in ClusterRole but bind it with a **RoleBinding** to keep it namespace-scoped:

```bash
kubectl create rolebinding dev-team-edit \
  --clusterrole=edit \
  --group=dev-team \
  -n dev
```

| ClusterRole | Access |
|---|---|
| `view` | Read-only (no secrets) |
| `edit` | Read/write most namespaced resources, including secrets |
| `admin` | Full control in the namespace, including RBAC for that namespace |
| `cluster-admin` | Everything, everywhere |

A `ClusterRole` + `RoleBinding` gives access only inside the RoleBinding's namespace.

## 9. Managed Clusters (EKS and AKS)

Client certificates are good for learning and kubeadm clusters. On managed clusters, authentication is delegated to the cloud, while **RBAC stays the same**.

### AWS EKS

- Authentication: AWS IAM identity (user or role) is mapped to a Kubernetes username/group.
- Mapping methods: **EKS access entries** (recommended) or the legacy `aws-auth` ConfigMap.
- Then create the same Role/RoleBinding for that group.

```bash
aws eks create-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::<ACCOUNT_ID>:user/ram \
  --kubernetes-groups dev-team
```

### Azure AKS

- Authentication: Microsoft Entra ID (Azure AD) users and groups.
- Bind an Entra group object ID as the RBAC subject:

```yaml
subjects:
- kind: Group
  name: "<ENTRA_GROUP_OBJECT_ID>"
  apiGroup: rbac.authorization.k8s.io
```

Alternatively, use Azure RBAC for Kubernetes authorization with built-in roles scoped to a namespace.

## 10. Summary

1. Kubernetes has no user objects; identity comes from certificates, OIDC, or cloud IAM.
2. Certificate `CN` is the user and `O` is the group.
3. Create key, CSR, then CertificateSigningRequest, approve it, and fetch the cert.
4. Build a kubeconfig with the cert and key.
5. Create a `Role` in the target namespace and a `RoleBinding` to the group.
6. Validate with `kubectl auth can-i`, `--as`, and a real kubeconfig, including negative tests.
