## Pods

### Key points

- A **Pod** is the **atomic unit of creation** in Kubernetes (k8s).
- Think of a Pod as a **small package with one or more containers** in it.
- Every Pod gets a **unique IP address** within the k8s cluster.
- Containers inside the same Pod **share resources**:
  - **Shared network** – all containers in a Pod share the same IP address and network namespace, so they can talk to each other over `localhost` and must use different ports.
  - **Shared storage** – volumes defined at the Pod level can be mounted by any container in that Pod.

![Pod overview](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s4.png?w=750&ssl=1)

### 1.2 Explanation

In plain Docker, the unit you work with is a container. Kubernetes adds a layer above it: the Pod. A Pod wraps one or more containers that must live together, be scheduled on the **same node**, and share the same lifecycle (they are created and destroyed together).

Because all containers in a Pod share one network namespace:

- They have **one IP** between them.
- Container A can reach container B at `localhost:<port>`.
- Two containers in the same Pod **cannot listen on the same port**.

Most Pods contain **only one container**. Multi-container Pods are used only when containers are tightly coupled.

### 1.3 Thinking about a typical application in Pods

The class used a typical application example to show how components map to containers and then to Pods.

- A typical application (see diagram):

  ![Typical application](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s5.png?w=750&ssl=1)

- If we have to run this in containers, we run **each component in its own container**:

  ![Components as containers](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s6.png?w=750&ssl=1)

- When it comes to Pods, consider the following mapping of containers to Pods:

  ![Containers mapped to pods](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s7.png?w=750&ssl=1)

**Design rule of thumb:** put containers in the *same* Pod only if they must scale together and share network/storage. Components that scale independently (for example, a frontend and a database) belong in **separate** Pods.

### 1.4 Scaling

- Each Pod can be scaled **horizontally** (more replicas of the Pod) or **vertically** (more CPU/memory per Pod) with the help of other k8s workload resources (such as Deployments).
- A bare Pod does not scale itself; that is the job of higher-level controllers (covered in later sessions).

### 1.5 Main container and sidecars

- When a Pod has more than one container:
  - The **primary container** is referred to as the **main container** (written `maincar` in the original notes, which is a typo for *main container*).
  - All the other containers are called **sidecars**.
- Typical sidecar uses: log shipping, metrics agents, proxies, config reloaders.

```
+-------------------------------- Pod (1 IP) --------------------------------+
|  +----------------+     +------------------+                                |
|  | main container |     | sidecar (logger) |    shared network + storage    |
|  +----------------+     +------------------+                                |
+----------------------------------------------------------------------------+
```

## 2. Interaction with the k8s cluster

### 2.1 Key points

- To interact with k8s we can use **any client that can send HTTP(S) requests**, because the k8s **api-server** exposes a REST API.
- k8s gives two simple options:
  - **kubectl** – a CLI tool that talks to the k8s api-server.
  - **Client libraries** – for programming languages. See the official list: <https://kubernetes.io/docs/reference/using-api/client-libraries/>

![Interacting with the cluster](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s8.png?w=750&ssl=1)

### 2.2 Security

- The k8s api-server is **HTTPS by default**.
- In the default configuration, the client must be **authenticated and authorized** to communicate with the cluster. An anonymous request is rejected.

### 2.3 The kubeconfig file

> **Note:** When we installed the cluster using **kubeadm**, on the **master (control-plane) node** there is a file called the **kube-config file**: `~/.kube/config`.

This file contains:

- **Certificate data** (credentials used to authenticate to the cluster)
- **api-server URLs** (the address of the cluster to connect to)

`kubectl` reads this file automatically, which is why you can type `kubectl get pods` without specifying a server address or credentials.

You can copy the same file to another machine (for example, your laptop) so that `kubectl` there can talk to the same cluster.

## 4. Imperative vs Declarative

`kubectl` allows interaction with k8s in two ways.

### 4.1 With commands (imperative)

We **construct a command** based on *what we want to do*.

![Imperative approach](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s9.png?w=750&ssl=1)

Example: `kubectl run --image httpd web1`

### 4.2 With manifest files (declarative)

We **create a YAML file** describing *what we want the end state to be* and then **apply** the file.

![Declarative approach 1](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s11.png?w=750&ssl=1)

![Declarative approach 2](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s10.png?w=750&ssl=1)

### 4.3 Comparison

| Aspect | Imperative (commands) | Declarative (manifests) |
|---|---|---|
| You describe | The *steps* / action | The *desired state* |
| Example | `kubectl run ...` | `kubectl apply -f pod.yaml` |
| Repeatable / version-controllable | Poor | Excellent (store YAML in Git) |
| Best for | Quick experiments, learning, troubleshooting | Day-to-day and production work |

> **Important:** We would use the **declarative approach for regular activities**. The imperative approach is used today just to get started.

## 5. Let's play with pods (imperative)

> Today's focus: the **imperative** way of creating Pods.

### 5.1 Create a pod named `web1` with an `httpd` container in it

**Syntax**

```bash
kubectl run <parameters> <name-of-pod>
```

**Example**

```bash
kubectl run --image httpd web1
```

What this does:

- Asks the api-server to create a Pod named **`web1`**.
- The Pod runs one container using the **`httpd`** (Apache HTTP Server) image, pulled from Docker Hub by default.
- The scheduler picks a node, and the kubelet on that node pulls the image and starts the container.

### 5.2 View the pods

```bash
kubectl get pods
```

Shows the Pod name, `READY` count (containers ready / total), `STATUS` (for example `Pending`, `ContainerCreating`, `Running`), `RESTARTS` and `AGE`.

### 5.3 View the pods with more info

```bash
kubectl get pods -o wide
```

Adds extra columns such as the Pod **IP address** and the **node** the Pod is running on.

![kubectl run / get pods](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s12.png?w=750&ssl=1)

### 5.4 Delete the pod

```bash
kubectl delete pod <name>
```

Example: `kubectl delete pod web1`

![kubectl delete pod](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s13.png?w=750&ssl=1)

### 5.5 Create a pod and exec into the container

We can create a pod and then **exec into the container** to run commands inside it.

![kubectl exec](https://i0.wp.com/directdevops.blog/wp-content/uploads/2026/06/k8s14.png?w=750&ssl=1)

A typical command for this is:

```bash
kubectl exec -it web1 -- bash
```

- `-i` keeps stdin open, `-t` allocates a terminal.
- Everything after `--` is the command run inside the container.
- Use `sh` instead of `bash` if the image does not include bash.

### 5.6 Command summary

| Task | Command |
|---|---|
| Create a pod | `kubectl run --image httpd web1` |
| List pods | `kubectl get pods` |
| List pods with IP/node | `kubectl get pods -o wide` |
| Delete a pod | `kubectl delete pod web1` |
| Run a command inside a pod | `kubectl exec -it web1 -- bash` |

## 8. How to write manifest files

Every k8s manifest is built from four top-level fields:

| Field | Who fills it | Purpose |
|---|---|---|
| `apiVersion` | You | Which API group/version defines this resource |
| `kind` | You | What type of object you are creating |
| `metadata` | You | Identity of the object (name, labels, annotations) |
| `spec` | You | Desired state (about 95% of your work) |
| `status` | **Kubernetes** | Current observed state |

The next sections explain each.

---

## 9. API versioning

### 9.1 Key points

- The k8s **api-server exposes k8s workloads as _resources_** (Pod, Deployment, Namespace and so on).
- k8s maintains **API versions** for them.
- k8s has an API versioning scheme: <https://kubernetes.io/docs/reference/using-api/#api-versioning>

### 9.2 Version levels

| Level | Format | Meaning |
|---|---|---|
| **alpha** | `v1alpha1`, `v1alpha2`... | Early, experimental, may be buggy or removed, usually disabled by default |
| **beta** | `v1beta1`, `v1beta2`... | Better tested, more stable, but may still change |
| **stable** | `v1`, `v2`... | Stable, supported for many releases; use this in production |

> The original notes write the alpha/beta formats as `v1alpha` and `v1beta`. In practice a number follows the level, e.g. `v1alpha1` or `v1beta1`.

**Rule of thumb:** prefer **stable** versions whenever available.

---

## 10. API groups and the `apiVersion` field

### 10.1 Key points

- k8s **groups multiple resources into API groups**.
- The `apiVersion` field is written as:

```
apiVersion: <group>/<version>

# if the group name is core, write the version directly
```

- The **core** group (also called the *legacy* group) has **no name**, so you write only the version, such as `v1`.

### 10.2 Example 1 – core group

- group: **core**
- Resource: **Pod**
- version: **v1**

```yaml
apiVersion: v1
kind: Pod
```

### 10.3 Example 2 – named group

- group: **apps**
- version: **v1**
- Resource: **Deployment**

```yaml
apiVersion: apps/v1
kind: Deployment
```

### 10.4 Core vs named groups

| Group | `apiVersion` format | Example resources |
|---|---|---|
| core | `v1` | Pod, Namespace, Service, ConfigMap, Secret, PersistentVolumeClaim |
| apps | `apps/v1` | Deployment, StatefulSet, DaemonSet, ReplicaSet |
| batch | `batch/v1` | Job, CronJob |
| networking.k8s.io | `networking.k8s.io/v1` | Ingress, NetworkPolicy |

> The core-group rows (`Pod`, `Namespace`, `PersistentVolumeClaim`) and the `apps` rows (`Deployment`, `StatefulSet`) were covered in class. The other examples are added for reference.

## 12. metadata

### 12.1 Key points

- `metadata` contains **information about the object** we are going to create.
- Major fields we will fill:
  - **name**
  - **labels**
  - **annotations**
- **For today, focus only on `name`.**

### 12.2 What each field is for

| Field | Purpose |
|---|---|
| `name` | Unique name of the object within its namespace |
| `labels` | Key-value pairs used to *select/group* objects (used heavily by Services, Deployments, etc.) |
| `annotations` | Key-value pairs for non-identifying extra information (tools, notes) |

Labels and annotations will be covered in later sessions.

### 12.3 Example 1 – Pod named `example-1`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example-1
```

### 12.4 Example 2 – Deployment named `deploy-1`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-1
```

---

## 13. spec

- `spec` is the field for **around 95% of what we do**.
- This is where we **provide our desired state**.
- To fill this field we **need to understand the functionality** of the resource. For example, to fill a Pod's `spec` you must know a Pod contains containers; to fill a Deployment's `spec` you must know about replicas, selectors and Pod templates.
- The structure of `spec` is different for every `kind`. Use the API reference to see which fields are available.

---

## 14. status

- `status` is **filled by Kubernetes, not by us**.
- It shows the **current/actual state** of the object (for example Pod phase, IPs, container states).
- k8s controllers continuously work to make **actual state (`status`) match desired state (`spec`)**. This is the heart of the declarative model.
- You will see `status` when you run `kubectl get pod <name> -o yaml`, but you **never write it** in your manifests.

## 15. Writing a Pod manifest

### 15.1 Key points

- A Pod has **container(s)**.
- Pod `spec` contains a `containers` list; each entry needs at minimum an `image` and a `name`.

### 15.2 Example 1 – Pod with an `httpd` container

> Write a manifest for a k8s Pod which has an **httpd image based container**.

```yaml
---
apiVersion: v1
kind: Pod
metadata:
  name: example-1
spec:
  containers:
    - image: httpd
      name: web
```

**Line-by-line explanation**

| Line | Meaning |
|---|---|
| `---` | YAML document separator (optional for a single document; useful when one file contains many objects) |
| `apiVersion: v1` | Pod belongs to the core group, version `v1` |
| `kind: Pod` | We are creating a Pod |
| `metadata.name: example-1` | The name of the Pod |
| `spec.containers` | A **list** of containers (note the `-` list item) |
| `image: httpd` | Image for the container |
| `name: web` | Name of the container inside the Pod (not the Pod name) |

> Containers in a Pod must have **unique names** within that Pod.

## 16. kubectl commands for manifests

### 16.1 Create the Pod

```bash
kubectl apply -f <filepath>
```

Example: `kubectl apply -f pod.yaml`

`apply` creates the object if it does not exist, and updates it if it does (declarative behaviour).

### 16.2 Delete the Pod

```bash
kubectl delete -f <filepath>
```

Deletes the objects defined in the file.

### 16.3 View the Pods

```bash
kubectl get pods
```

### 16.4 More info on Pods

```bash
kubectl get pods -o wide
```

### 16.5 Detailed info

```bash
kubectl describe pod <name>
```

`describe` shows full details: image, node, IP, labels, container state, and an **Events** section at the bottom, which is the first place to look when a Pod does not start (for example, image pull errors).

### 16.6 Command summary

| Command | Purpose |
|---|---|
| `apply` | Create/update objects from a file |
| `delete` | Delete objects |
| `describe` | Detailed view of an object, including events |
| `get` | List objects |

> **Terminology:** In k8s, what we create is referred to as **objects**.

### 16.7 Typical workflow

```bash
# 1. write the manifest
vi pod.yaml

# 2. create
kubectl apply -f pod.yaml

# 3. check
kubectl get pods
kubectl get pods -o wide
kubectl describe pod example-1

# 4. clean up
kubectl delete -f pod.yaml
```

## 17. kubectl api-resources

kubectl has an interesting command:

```bash
kubectl api-resources
```

It lists all resource types the cluster supports, with columns such as:

| Column | Meaning |
|---|---|
| `NAME` | Resource name (plural), such as `pods` |
| `SHORTNAMES` | Abbreviations, such as `po`, `deploy`, `ns` |
| `APIVERSION` | The `group/version` to put in your manifest's `apiVersion` |
| `NAMESPACED` | Whether the resource lives inside a namespace |
| `KIND` | The value to put in your manifest's `kind` |

This is a quick way to find the correct `apiVersion` and `kind` straight from your cluster, without the website.

Related helper (useful, not covered in class): `kubectl explain pod.spec` shows the fields available under a given path.

## 18. Exercises (with sample solutions)

### Exercise 1

> Write a spec to create a **mysql** container and pass an **environment variable for the root password**.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mysql-pod
spec:
  containers:
    - name: mysql
      image: mysql
      env:
        - name: MYSQL_ROOT_PASSWORD
          value: "ChangeMe123"
```

Notes:

- The official `mysql` image requires `MYSQL_ROOT_PASSWORD` (or an equivalent option) to start; otherwise the container exits.
- `env` is a **list** of `name` / `value` pairs.
- Hardcoding a password is acceptable for practice only. Real workloads should use a **Secret** (covered later).

### Exercise 2

> Write a spec to create an **nginx** container and **fill the port information**.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
    - name: nginx
      image: nginx
      ports:
        - containerPort: 80
```

Notes:

- `containerPort` documents the port the container listens on. It is informational and does not by itself expose the Pod outside the cluster (that is the job of Services).

### Verify both

```bash
kubectl apply -f mysql-pod.yaml
kubectl apply -f nginx-pod.yaml
kubectl get pods -o wide
kubectl describe pod mysql-pod
kubectl delete -f mysql-pod.yaml
kubectl delete -f nginx-pod.yaml
```

## 19. Quick revision cheat sheet

### Concepts

- **Pod** = smallest deployable unit; 1+ containers; **one IP**; shared network and storage.
- Main container + **sidecars** in multi-container Pods.
- Clients talk to the **api-server** over HTTPS; credentials and URL live in `~/.kube/config`.
- Two styles: **imperative** (commands) and **declarative** (YAML + `apply`). Use declarative for regular work.

### Manifest skeleton

```yaml
apiVersion: <group>/<version>   # core group => just v1
kind: <Kind>
metadata:
  name: <name>
spec:
  # desired state (depends on kind)
# status: filled by k8s, never written by you
```

### API versions

`alpha` (`v1alpha1`) < `beta` (`v1beta1`) < **stable** (`v1`, `v2`)

### Common `apiVersion` / `kind` pairs

| kind | apiVersion |
|---|---|
| Pod | `v1` |
| Namespace | `v1` |
| PersistentVolumeClaim | `v1` |
| Deployment | `apps/v1` |
| StatefulSet | `apps/v1` |

### Commands

```bash
kubectl run --image httpd web1        # imperative pod
kubectl get pods [-o wide]
kubectl describe pod <name>
kubectl exec -it <pod> -- bash
kubectl delete pod <name>

kubectl apply -f <file>               # declarative create/update
kubectl delete -f <file>              # declarative delete
kubectl api-resources                 # list resources, groups, kinds
```
